# AgentHub 产品蓝图与阶段路线

## 1. 一句话方向

AgentHub 最终要实现为一个**基于 Go 与 Eino 的、可部署的 Agent 应用平台**：开发者可以配置 Agent、连接模型与工具、接入 MCP、管理会话与知识库、运行工作流，并通过终端、HTTP API 和最小 Web 控制台使用和观察整个执行过程。

它不是只展示设计模式的代码仓库，也不是重新实现一遍 Eino。

## 2. 为什么做这个项目

这个项目同时有两个目标，但必须明确主次和切换点。

### 2.1 学习目标

通过一条真实可运行链路理解：

- 模型消息如何流动；
- Agent 为什么会循环调用模型和工具；
- ToolCall 与 ToolResult 如何关联；
- Memory 为什么要区分完整历史与模型视图；
- 流式响应、错误传播和资源关闭为什么复杂；
- 工厂、适配器、注册中心分别在什么问题出现后才有价值；
- HTTP、数据库、可观测性如何包围而不是侵入 Agent 核心逻辑。

### 2.2 产品目标

最终交付的不是一个 Runtime 库，而是一个可以启动和使用的 AgentHub：

1. 能创建和配置多个 Agent。
2. 能绑定不同模型、系统提示词、工具、MCP Server 和知识库。
3. 能进行同步与流式对话。
4. 能保存会话、消息和执行记录。
5. 能回答知识库问题并给出检索引用。
6. 能运行至少一种工作流或多 Agent 协作场景。
7. 能观察每次模型调用、工具调用、耗时、Token 和错误。
8. 能通过 Docker Compose 在本地或服务器启动。
9. 能通过 HTTP API 使用，并提供一个用于演示和调试的最小 Web 控制台。

## 3. 最终用户看到的产品

### 3.1 使用入口

#### 终端 CLI

用于教学、调试和最短反馈：

- 选择 Agent；
- 连续对话；
- 查看流式输出；
- 展开本轮模型调用和工具调用；
- 快速验证 MCP、Memory 和 RAG 行为。

#### HTTP API

用于真实集成：

- Agent 配置管理；
- 会话与消息接口；
- 同步聊天与 SSE 流式聊天；
- 工具、MCP Server 和知识库管理；
- 运行记录与健康检查。

#### 最小 Web 控制台

用于让最终成果可见、可演示，但不把课程变成前端项目：

- Agent 列表和配置页；
- Playground 对话页；
- 工具与 MCP 状态页；
- 知识库上传与检索页；
- 单次运行详情页，展示步骤、耗时、Token 和错误。

Web 控制台放在 API 稳定之后实现。它只覆盖核心流程，不追求完整低代码搭建器和复杂设计系统。

### 3.2 一个最终可演示场景

最终验收时，用户能够完成下面这条完整链路：

1. 启动 AgentHub、数据库和必要依赖。
2. 在控制台创建“项目知识助手”。
3. 选择一个模型，填写系统提示词。
4. 挂载一个本地工具和一个 MCP 工具。
5. 上传一份项目文档并完成索引。
6. 在 Playground 提问。
7. 页面流式显示回答。
8. Agent 按需调用工具或检索知识库。
9. 回答展示引用来源。
10. 运行详情中能看到模型、工具、检索、Token、耗时和错误。
11. 服务重启后，Agent 配置、知识库和历史会话仍然存在。

## 4. 产品边界

### 4.1 本项目自己负责

这些决定了 AgentHub 是什么产品，应该由项目代码掌握：

- Agent 配置、版本和启停；
- 应用用例与业务流程；
- 会话、消息和运行记录；
- API 协议、SSE 事件和错误响应；
- 本地工具与 MCP Server 的产品化管理；
- 知识库、文档、索引任务和引用信息；
- 权限边界、配置管理和敏感信息保护；
- 运行观测、评测入口和部署方式；
- CLI 与最小 Web 控制台。

### 4.2 交给 Eino

以下属于成熟框架的通用能力，不继续长期重复建设：

- ChatModel、Tool、Retriever 等通用组件协议；
- 模型厂商适配；
- ReAct Agent 的通用循环；
- 流的拼接、转换、复制和合并；
- Graph、Chain、Workflow 编排；
- 回调与横切观测注入；
- 常见 Agent 模式、多 Agent 运行基础和中断恢复能力。

Eino 官方将自身定位为 Go 的 LLM 应用开发框架，并提供组件抽象、Agent 能力、Graph/Workflow 编排、流处理和回调机制：

- https://github.com/cloudwego/eino
- https://cloudwego.cn/docs/eino/overview/
- https://www.cloudwego.io/docs/eino/core_modules/flow_integration_components/react_agent_manual/

### 4.3 当前自研 Runtime 的归宿

Phase C 收口后，自研 Runtime 及其配置、测试和早期 MCP 协议实验已经整体迁入 `examples/selfbuilt-runtime/`，成为理解 Agent 内核的封闭实验台；根 `internal/` 只保留继续演进的生产应用代码。

处理原则：

1. Phase A 先把它们接进真实入口，亲眼观察完整循环。
2. Phase B 用 Eino 实现同一条链路，逐项比较概念映射。
3. 比较后记录架构决策：生产主线使用 Eino。
4. 业务层不得同时依赖两套 Runtime。
5. 自研实现已经移入 `examples/selfbuilt-runtime/internal/`；嵌套 `internal` 的编译期导入边界阻止生产代码依赖，不继续扩展成第二套生产框架。

### 4.4 明确不做

首个完整版本不做：

- 自研通用 Agent 框架或 Eino 替代品；
- 模型训练、微调平台或 GPU 调度；
- 面向公网的多租户 SaaS、计费和商业化系统；
- 完整复制 Coze 类可视化低代码平台；
- 任意代码的开放执行沙箱；
- 大规模分布式调度和跨地域高可用；
- 为覆盖率而写的大量低价值单元测试。

这些非目标能防止学习项目再次因范围失控而只剩架构。

## 5. 目标系统边界

总览图：[`docs/images/agenthub-product-roadmap.svg`](images/agenthub-product-roadmap.svg)

```text
CLI / Web Console / External Client
                 │
          HTTP API + SSE
                 │
       Application Use Cases
  Agent / Chat / Session / Knowledge / Run
                 │
    最小应用边界（从真实用例中提取）
                 │
              Eino
     Agent / Tool / Stream / Graph / RAG
                 │
 ┌───────────────┼────────────────┐
模型 Provider   本地工具 / MCP   数据与可观测性
                              PostgreSQL / Vector / Trace
```

这里最重要的不是立即创建一个名为 `Agent Runtime Port` 的接口，而是保持职责方向：AgentHub 的业务用例负责产品语义，Eino 负责通用 Agent 执行，不让 API、数据库和业务对象无边界地扩散成框架类型。

B.4 只记录这项边界决策，不新增接口。等 Phase C 的 CLI 用例或 Phase E 的 HTTP 用例产生真实重复、耦合或明确变化来源后，再从具体代码中提取最小应用接口；若直接调用 Eino 已足够清晰，则不为形式额外包装。

## 6. 版本里程碑

| 里程碑 | 用户获得什么 | 对应阶段 |
|---|---|---|
| M0 看懂内核 | 能运行并解释一次模型—工具闭环 | Phase A |
| M1 可用 CLI Agent | 真实模型、多轮对话、工具和流式输出 | Phase B—C |
| M2 Agent 服务 MVP | 可通过 API 与 Web Playground 使用，数据可保存 | Phase D—F |
| M3 知识 Agent | 可上传文档、检索并带引用回答 | Phase G |
| M4 编排平台 | 可运行一个有明确价值的 Workflow/Multi-Agent 场景 | Phase H |
| V1 可部署 AgentHub | 有配置、观测、评测、稳定性和 Docker 交付 | Phase I |

## 7. 分阶段详细路线

## Phase A：恢复可见主线——看懂自研 Agent 内核

### 阶段问题

已有很多包和单测，但应用入口没有运行 Agent，学习者无法把零件与用户行为联系起来。

### 阶段目标

只用本地演示组件，跑通并解释：

```text
终端输入 → Agent → Model → Tool → Model → 最终回答
```

### 课程拆分

#### A.0 现状地图与运行基线

- 运行当前入口，记录实际输出。
- 区分“已经实现”“已经串联”“用户可见”“已经理解”。
- 标出入口没有调用的 Runtime 包。
- 交付：当前调用链图和能力盘点。

#### A.1 最小终端 Agent：直接回答

- 在生产代码中提供一个最小演示 Model。
- 从 `main` 创建 Registry、Memory 和 Agent。
- 输入一条 User Message，输出 FinalMessage、Steps 和 Usage。
- 学习重点：依赖组装、接口的运行时实现、入口与业务逻辑的边界。

#### A.2 本地工具闭环

- 添加一个简单、无外部依赖的工具。
- 演示 Model 第一轮返回 ToolCall，第二轮根据 ToolMessage 给出答案。
- 终端打印模型步骤、工具名称、参数、结果和最终回答。
- 学习重点：为什么普通聊天不等于 Agent、消息顺序、Call ID、业务错误与流程错误。

#### A.3 真实调用链复盘

- 从 `main` 开始逐方法跟踪一次成功调用。
- 每个关键方法回答：谁调用、输入、输出、副作用、错误去向、存在理由。
- 审视 Registry、Executor、Factory 是否都对当前链路有可解释价值。

#### A.4 最小纵向测试

- 增加一个保护完整入口或应用用例的测试。
- 只保留本阶段最重要的成功路径和失败边界。
- 解释旧测试各自保护的系统行为，暂不为了覆盖率扩展用例。

### 阶段交付

- 可运行的终端演示；
- 自研 Agent Loop 调用链图；
- 一条纵向测试；
- 一份“保留、简化、等待比较”的 Runtime 组件清单。

### 完成标准

- `go run ./examples/selfbuilt-runtime` 会真实运行一次自研 Agent 教学闭环。
- 学习者能不看代码讲清两轮模型调用中消息如何变化。
- 学习者能解释 Registry 与 Executor 的区别。
- 不接真实模型、不接 Eino、不做 HTTP。

## Phase B：Eino 对照实验——从理解内核切换到使用框架

### 阶段问题

继续扩展自研 Runtime 会重复建设 Eino 已有的通用能力；直接切换又会让框架变成黑盒。

### 阶段目标

使用 Eino 重做 Phase A 的同一条链路，以行为和概念一一对照，然后确定唯一生产主线。

### 课程拆分

#### B.1 Eino 最小直接回答对照

- Phase A 的自研 Runtime 作为冻结基线，不再添加新特性。
- 引入并锁定明确版本的 Eino。
- 使用 Eino ChatModel 与 Chain 运行和 A.1 等价的直接回答。
- 对照项目 Message、Model、Agent.Run 与 Eino 的 schema.Message、BaseChatModel、Chain/Runnable。

#### B.2 Eino 工具闭环

- 使用 Eino Tool 与 Agent 复现 A.2。
- 对照自研 Registry/Executor/Loop 与 Eino Tool/ToolsNode/Agent。
- 观察 Eino 如何管理工具绑定、历史和结束条件。

#### B.3 流式和回调观察

- 用最小例子观察 Eino 的流式输出。
- 添加回调记录模型与工具节点的开始、结束和错误。
- 不先封装，先看框架真实行为。

#### B.4 架构决策与生产切换

- 写 ADR，记录为什么生产主线采用 Eino。
- 确定 AgentHub 应用层与 Eino 之间最小适配边界。
- 保证生产入口只选择一套 Runtime。

#### B.5 清理双轨风险

- 自研 Runtime 明确标记为学习实现，或迁移到独立学习目录。
- 删除没有继续保留价值的重复生产封装和测试。
- 保留能解释核心原理的少量高价值示例。

### 阶段交付

- Eino 版最小 Agent；
- 自研概念到 Eino 概念的对照表；
- Runtime 选型 ADR；
- 单一生产入口。

### 完成标准

- 同一个终端用例可以用 Eino 跑通。
- 学习者能说出 Eino 替代了哪些自研代码，以及没有替代哪些 AgentHub 业务能力。
- 生产路径不存在两套并行 Agent Loop。

## Phase C：可用 CLI Agent——连接真实模型

### 阶段问题

演示 Model 只能验证控制流，不能回答真实问题。

### 阶段目标

实现一个真正可连续使用、可观察、可安全配置的终端 Agent。

### 课程拆分

#### C.1 真实模型接入

- 接入一个支持工具调用的模型 Provider。
- 使用环境变量读取密钥与模型配置。
- 对缺少配置、鉴权失败、超时进行清晰报错。

#### C.2 交互式 CLI

- 支持循环读取用户输入和显式退出。
- 将应用启动、Agent 创建和单轮聊天拆成可解释的用例。
- 不把终端 I/O 写入 Runtime。

#### C.3 真实本地工具

- 提供一个有实际价值且副作用可控的工具。
- 让模型自主决定是否调用，而不是在业务代码中写死。
- 展示工具参数校验和失败反馈。

#### C.4 流式输出

- 终端实时输出文本增量。
- 明确“一次模型流结束”和“整个 Agent 运行结束”的区别。
- 处理中断、关闭和半途失败。

#### C.5 多轮上下文与 Memory

- 连续问题共享会话历史。
- 显示完整历史、发送给模型的视图和裁剪原因。
- 再决定使用 Eino 上下文能力还是 AgentHub 会话策略。

### 阶段交付

- 可连续对话的 CLI；
- 一个真实模型适配；
- 一个真实本地工具；
- 流式输出和可观察的 Memory 行为。

### 完成标准

- 学习者可以在终端完成多轮问答和一次自主工具调用。
- 密钥不进入配置文件、日志或 Git。
- 断网、超时、无效工具参数至少各验证一次。

## Phase D：工具中心与 MCP——扩展 Agent 能力

### 阶段问题

本地硬编码工具难以扩展，现有 MCP 代码又只有协议边界和测试替身。

### 阶段目标

让 AgentHub 能配置、发现、调用并观察本地工具与真实 MCP 工具。

### 课程拆分

#### D.1 工具目录

- 统一展示 Agent 可用工具及其来源、描述和参数。
- 区分本地工具、MCP 工具与禁用工具。

#### D.2 单 MCP Server 真实连接

- 选择一种最简单的 MCP 传输方式。
- 建立真实 Session，发现工具并从 CLI 调用。
- 对照现有 Session 与 ToolAdapter，决定复用或替换范围。

#### D.3 多 Server 与名称冲突

- 接入两个 Server。
- 验证同名工具的命名空间和配置可读性。
- 复用已有 Manager 行为或迁移到 Eino/MCP 集成层。

#### D.4 生命周期与稳定性

- 在真实连接上观察超时、断开和关闭。
- 再实现有限重试、状态管理和优雅关闭。
- 明确哪些错误可交给模型，哪些必须终止流程。

#### D.5 MCP 配置与诊断

- 支持从配置添加、启用和禁用 Server。
- 提供连接测试、工具列表和最近错误。
- 敏感参数只引用环境变量或安全配置来源。

### 阶段交付

- 一个真实 MCP 集成；
- 可查询的工具目录；
- 多 Server 管理；
- 生命周期和错误诊断。

### 完成标准

- CLI 能列出并调用至少一个真实 MCP 工具。
- 同名工具不会冲突。
- Server 不可用时，用户能看见明确原因，进程能正确释放资源。

## Phase E：HTTP API 与最小 Web Playground

### 阶段问题

CLI 只能供本地单人调试，不能被其他应用调用，也不能清晰展示产品形态。

### 阶段目标

把已经工作的 Agent 用例暴露为稳定 API，并提供最小可视化使用入口。

### 课程拆分

#### E.1 HTTP 服务骨架

- 实现 Server 生命周期、路由和 `GET /health`。
- 请求处理只调用应用用例，不复制 Agent 逻辑。

#### E.2 同步聊天 API

- 实现 `POST /api/chat`。
- 定义请求、响应、错误码和参数校验。
- 使用内存会话标识串起多轮消息。

#### E.3 SSE 流式聊天

- 实现 `POST /api/chat/stream` 或等价接口。
- 定义稳定事件：文本增量、工具开始、工具结束、完成和错误。
- 验证客户端断开后的取消传播。

#### E.4 基础中间件

- 请求 ID、结构化访问日志、panic 恢复、超时和基础认证。
- 每项中间件都由一个可观察问题驱动。

#### E.5 最小 Web Playground

- Agent 选择；
- 输入与流式回答；
- 展开查看工具调用；
- 清空或新建会话；
- 展示错误状态。

#### E.6 API 文档

- 接口稳定后生成 OpenAPI。
- 使用真实请求做 smoke test。

### 阶段交付

- HTTP/SSE 服务；
- 最小 Web Playground；
- OpenAPI；
- API smoke test。

### 完成标准

- 浏览器可以完成一次流式对话和工具调用。
- CLI 与 HTTP 复用同一应用用例。
- 客户端中断不会留下持续运行的模型或工具调用。

## Phase F：会话与配置持久化

### 阶段问题

服务重启后，Agent 配置和对话全部丢失。

### 阶段目标

持久化 Agent、会话、消息和运行摘要，让产品状态可恢复。

### 课程拆分

#### F.1 数据模型与存储边界

- 从已有 API 行为反推最小表结构。
- 定义 Agent、Conversation、Message 和 RunRecord。
- 先写用例接口，再选择数据库实现。

#### F.2 数据库与迁移

- 默认路线采用 PostgreSQL，以贴近企业 Go 服务。
- 建立连接池、健康检查和版本化迁移。
- 本地开发通过容器提供数据库。

#### F.3 Repository 与事务

- 只为真实用例实现必要查询。
- 保证一轮聊天写入的一致性。
- 验证回滚和唯一约束错误。

#### F.4 Agent 配置管理

- 创建、查询、更新、启停 Agent。
- 配置引用模型、提示词、工具、MCP 和 Memory 策略。
- 敏感配置不直接存储明文。

#### F.5 历史恢复

- 读取历史会话继续聊天。
- 服务重启后恢复 Agent 与会话。
- 处理不存在、已禁用和版本不兼容的配置。

### 阶段交付

- PostgreSQL Schema 与迁移；
- Agent CRUD；
- 会话与消息持久化；
- 重启恢复演示。

### 完成标准

- 服务重启后可以继续原会话。
- 数据库失败不会被伪装成模型错误。
- Repository 只承载持久化，不包含 Agent 编排。

## Phase G：知识库与 RAG——完成知识 Agent

### 阶段问题

模型只能依赖预训练知识和会话上下文，不能可靠回答用户文档问题。

### 阶段目标

上传文档、建立索引、检索证据，并生成带来源引用的回答。

### 课程拆分

#### G.1 文档与索引任务

- 支持最小文件类型，例如 Markdown、TXT 和 PDF。
- 保存文档元数据和索引状态。
- 失败任务可以重试并显示原因。

#### G.2 解析与切分

- 保留文档、页码或章节来源信息。
- 比较固定长度与结构化切分。
- 用实际问答效果决定参数，而不是先做复杂策略。

#### G.3 Embedding 与向量存储

- 接入 Embedding 组件。
- 使用 pgvector 或与 PostgreSQL 配套的向量能力。
- 验证相似度查询和过滤条件。

#### G.4 Retriever 与引用

- 返回 Top-K 文档片段和来源元数据。
- 在回答中保留可追踪引用。
- 展示“检索到了什么”，便于调试错误回答。

#### G.5 RAG Agent

- 将 Retriever 作为 Agent 能力接入。
- 区分无证据、证据冲突和正常回答。
- 防止没有命中资料时伪造引用。

#### G.6 知识库页面与评测集

- 上传、查看、删除文档；
- 展示索引状态和检索结果；
- 建立一组可重复问答评测样例。

### 阶段交付

- 知识库 API 与页面；
- 文档索引流水线；
- 带引用的 RAG 问答；
- 最小评测集。

### 完成标准

- 上传一份文档后能回答至少一组可核对问题。
- 每条知识性结论可以定位到检索片段。
- 删除文档后相关检索结果消失。

## Phase H：Workflow 与 Multi-Agent——证明编排价值

### 阶段问题

不能为了“高级”而引入多 Agent；必须先找到单 Agent 明显不适合的任务。

### 阶段目标

选定一个可比较的复杂任务，用 Eino Graph/Workflow 或 Agent 协作显著改善可控性或结果质量。

### 推荐基准场景

“研究并生成项目技术方案”：

1. Planner 拆解问题；
2. Researcher 查询知识库和工具；
3. Writer 形成结构化方案；
4. Reviewer 检查证据和遗漏；
5. 必要时由用户确认后继续。

### 课程拆分

#### H.1 单 Agent 基线

- 先用当前 Agent 完成同一任务。
- 记录质量、耗时、调用步骤和失败点。

#### H.2 确定性 Workflow

- 使用 Eino Graph/Workflow 编排固定步骤。
- 观察节点输入输出、状态和分支。

#### H.3 多 Agent 协作

- 只拆分真正不同的角色职责。
- 明确上下文传递和最终聚合者。
- 不创建没有独立价值的角色。

#### H.4 Human-in-the-loop

- 在高成本或有副作用的步骤前暂停。
- 保存检查点并允许恢复。

#### H.5 并行与失败处理

- 对独立任务并行执行。
- 设置并发上限、部分失败策略和结果排序。

### 阶段交付

- 一个真实 Workflow/Multi-Agent 场景；
- 单 Agent 与编排方案的对照结果；
- 状态、分支、中断和恢复记录。

### 完成标准

- 能用证据说明为什么这个场景需要 Workflow 或多 Agent。
- 任一节点失败时，运行记录能指出失败位置。
- 用户可以在暂停点确认、拒绝或恢复。

## Phase I：可观测、评测、稳定性与部署——达到 V1

### 阶段问题

“本机能跑”不等于可维护、可诊断和可交付。

### 阶段目标

让 AgentHub 可以被稳定启动、观察、评估和部署。

### 课程拆分

#### I.1 运行记录与 Trace

- 为一次 Agent Run 生成统一标识。
- 串联 HTTP、模型、工具、检索和数据库操作。
- 页面能查看步骤时间线和错误位置。

#### I.2 指标

- 请求量、成功率和延迟；
- 模型调用次数、Token 和耗时；
- 工具/MCP 成功率和耗时；
- 检索耗时和命中情况。

#### I.3 评测

- 建立离线样例集和可重复运行入口。
- 区分确定性断言、引用正确性和主观质量评分。
- 模型或 Prompt 变更前后可以比较。

#### I.4 稳定性

- 超时预算和取消传播；
- 有边界的重试；
- 限流、并发控制和熔断；
- 优雅关闭和资源释放。

#### I.5 安全基线

- API 认证；
- 输入大小和文件类型限制；
- 工具权限与副作用分级；
- 密钥脱敏；
- Prompt Injection 和越权工具调用的基础防护。

#### I.6 Docker 与 CI

- 多阶段镜像；
- Docker Compose 启动应用与数据库；
- 开发、测试、生产配置分离；
- CI 执行格式化检查、测试、静态检查和构建。

#### I.7 V1 验收演示

- 从零环境启动；
- 创建 Agent；
- 连接模型和 MCP；
- 上传知识文档；
- 发起带引用的流式问答；
- 查看运行记录；
- 重启并恢复数据。

### 阶段交付

- Trace、指标和运行详情；
- 最小评测系统；
- 稳定性与安全基线；
- Docker Compose 与 CI；
- V1 演示手册。

### 完成标准

- 新环境可根据文档启动完整系统。
- 核心演示链路全部可重复执行。
- 关键失败可以从日志、指标或 Trace 定位。
- 自动检查通过，仓库不包含密钥和敏感配置。

## 8. 技术路线总表

| 领域 | 目标选择 | 引入阶段 | 为什么 |
|---|---|---|---|
| 语言 | Go | 已确定 | 项目核心学习目标 |
| Agent Runtime | Eino | Phase B | 使用成熟组件、Agent、流和编排能力 |
| 自研 Runtime | 教学实验台 | Phase A—B | 理解原理，不作为长期双轨生产实现 |
| CLI | Go 标准输入输出 | Phase A—C | 最短反馈与调试入口 |
| HTTP | Go HTTP 框架在 Phase E 前再选 | Phase E | 避免提前做无场景的框架选型 |
| 流式协议 | SSE | Phase E | 浏览器与 API 客户端易接入 |
| 主数据库 | PostgreSQL | Phase F | 会话、配置和运行记录的可靠存储 |
| 向量存储 | 优先 pgvector | Phase G | 减少学习阶段基础设施数量 |
| MCP | 真实 SDK/传输 + AgentHub 配置层 | Phase D | 扩展外部工具生态 |
| Web 控制台 | 最小前端，API 稳定后选型 | Phase E | 让成果可见，但不抢占 Go 主线 |
| 可观测性 | OpenTelemetry + 指标系统 | Phase I | 贯通模型、工具、检索和 API |
| 部署 | Docker Compose | Phase I | 提供可重复本地与服务器环境 |

所有尚未实际进入阶段的库和框架都不提前加入依赖。开始对应阶段时，先做小型技术验证，再在计划中锁定版本和选择。

## 9. 每个阶段统一完成条件

一个阶段只有同时满足以下条件才完成：

1. **可用**：从真实入口完成本阶段用户场景。
2. **可见**：能直接观察输入、关键步骤、输出和失败。
3. **可解释**：学习者能沿调用链解释关键文件与方法。
4. **有边界**：明确本阶段没有做什么，避免范围蔓延。
5. **有验证**：运行最小但有效的测试、静态检查或构建。
6. **有文档**：更新计划、接口说明和有长期价值的图示。
7. **有检查点**：只提交本阶段相关文件，不自动推送。

## 10. 路线调整规则

路线是可校准的，不是不可变的大纲。出现以下任一情况时暂停并复盘：

- 连续两节课没有新增用户可见行为；
- 新增抽象无法指出当前调用者和当前问题；
- 测试代码显著增长，但没有新的运行场景；
- 同一能力在自研 Runtime 和 Eino 中重复扩展；
- 为未来功能提前引入数据库、队列、缓存或复杂框架；
- 学习者无法解释上一节的关键调用链。

复盘后可以简化、删除或调换课程，产品目标不因原大纲而让位。
